1. PURPOSE

This specification converts the ratified AFF-001 Phase D Technical Architecture into deterministic, implementation-ready MVP requirements.

Its governing question is:

EXACTLY WHAT MUST BE BUILT FOR THE PRIVATE AFFILIATE MVP TO WORK END TO END?

The future implementation shall not require a developer, Codex session, Antigravity session, workflow author, database engineer, or AI agent to invent affiliate policy, attribution rules, commission rules, financial state transitions, payout authority, or audit behavior.

Where an unresolved business, legal, economic, or vendor decision remains, this specification explicitly marks:

TBD — REQUIRES PROJECT OWNER / GOVERNANCE / IMPLEMENTATION VALIDATION

This document specifies implementation behavior.

It does not authorize implementation.

2. GOVERNING PRINCIPLES

The MVP shall obey the following rules:

1. EXTEND THE SPINE. DO NOT BUILD A PARALLEL BODY.

2. WooCommerce remains transaction truth.

3. CCSS remains approved commercial-product truth.

4. BROS/Supabase remains affiliate identity, attribution, commission, ledger, dispute, audit, and payout-preparation truth.

5. Budly remains an education, relationship, support, interpretation, and assistance layer.

6. n8n remains orchestration, not policy authority or financial truth.

7. The existing bros.revenue_event.v1 pipeline shall be reused.

8. Affiliate commission processing occurs at WooCommerce order-line level.

9. Financial arithmetic shall use exact decimal values.

10. Financial history is append-only.

11. Corrections create new records or events.

12. Financial ambiguity fails closed.

13. Duplicate events must never create duplicate money.

14. Client-supplied affiliate information is never trusted without server-side validation.

15. Human authorization remains mandatory for affiliate approval where required, Strategic Partner approval, binding disputes, exceptional financial adjustments, termination, and private-pilot payout authorization.

16. No raw tax documents belong in ordinary affiliate CRM records.

17. Affiliate-facing systems shall not expose customer identity merely because the affiliate generated a conversion.

18. The private pilot succeeds only after one complete referral-to-reconciled-payout round trip is proven.

The financial safety doctrine is:

DO NOT GUESS. DO NOT PAY. DO NOT ERASE.

4. DATABASE MODEL

PostgreSQL shall be used.

Primary internal entities shall use UUID primary keys unless this specification explicitly defines another immutable business identifier.

All timestamps shall be timestamptz stored in UTC.

Currency amounts shall use numeric(20,6) internally unless the implementation validates a stricter currency-safe precision without information loss. User-facing payment amounts may be rounded to the applicable currency minor unit only at defined settlement boundaries.

JSON fields shall use jsonb.

No financial table may use IEEE floating-point types for monetary calculation.

6. AFFILIATE ID CONTRACT

Canonical public affiliate identifier:

AFF-######

Regex:

^AFF-[0-9]{6}$

Initial range:

AFF-000001 through AFF-999999.

Generation shall use a database sequence reserved exclusively for affiliate codes.

The sequence value is formatting input only. The database UUID remains the relational primary key.

Requirements:

- generated only after application approval;

- not generated for declined applications;

- globally unique;

- never reused;

- never renumbered;

- never changed after issuance;

- survives name, email, class, suspension, inactivity, and termination changes;

- contains no PII;

- may be exposed in affiliate links and affiliate-facing interfaces;

- sequence gaps are valid and must not be repaired.

10. QR CONTRACT

Canonical route:

/aq/{affiliate_id}/{qr_id}

A valid QR request must resolve both IDs to the same active governed record.

A QR scan creates a normal qualified referral event with method QR.

Financial priority is identical to a referral link.

A subsequent valid referral from another affiliate may replace it under last-qualified-referral.

A valid attributing affiliate coupon may override it.

QR records may be disabled without destroying historical scans.

Destination changes modify the QR registry, not the printed QR.

11. ATTRIBUTION ALGORITHM

Attribution version for initial MVP:

AFF-ATTR-v1

11.1 Ordered checkout resolution

INPUT:

  authoritative Woo order

  normalized revenue event

  validated coupon identities

  server-side referral history/context

1. Verify event authenticity and idempotency.

2. Resolve Woo order and transaction state.

3. Resolve any valid attributing affiliate coupon.

4. IF exactly one valid attributing affiliate coupon exists:

      candidate = coupon affiliate

      method = AFFILIATE_COUPON

   ELSE IF multiple conflicting attributing affiliate coupons exist:

      status = UNRESOLVED

      quarantine

      STOP financial processing

   ELSE:

      find latest QUALIFIED referral event:

          occurred_at <= qualifying transaction timestamp

          attribution_expires_at >= qualifying transaction timestamp

          affiliate was eligible under applicable governance

          event validation_status = QUALIFIED

      IF found:

          candidate = referral affiliate

          method = method from winning referral

      ELSE:

          status = UNATTRIBUTED

          create auditable no-attribution decision

          STOP affiliate commission processing without error

5. Validate candidate affiliate and transaction eligibility.

6. IF attribution is financially ambiguous:

      status = UNRESOLVED

      quarantine

      STOP

7. Write immutable attribution decision.

8. Continue product eligibility and commission processing.

11.2 Last-qualified referral

For ordinary LINK and QR referrals:

winner = MAX(occurred_at) among valid, non-expired qualified referrals.

Prior referrals remain append-only.

11.3 Coupon precedence

A valid attribution_enabled=true affiliate coupon overrides LINK/QR referral attribution.

A NON_ATTRIBUTING or disabled coupon has no affiliate financial effect.

11.4 Expiration

attribution_expires_at = qualified_referral_occurred_at + interval '30 days'

Expiry is evaluated against the qualifying transaction timestamp, not webhook-processing time.

11.5 Suspended/inactive affiliate behavior

New referral events from non-ACTIVE affiliates do not qualify.

Whether a previously valid referral survives a later status change shall follow the effective suspension/termination decision.

Default private-pilot behavior:

- suspension places affected unresolved financial processing under review;

- suspension does not silently confiscate previously earned valid commission;

- termination stops future referral qualification;

- historical entitlement remains subject to its original rules and any documented enforcement decision.

11.6 Existing customer

Existing-customer status does not block affiliate attribution for a new qualifying purchase.

11.7 Manual override

Manual attribution correction requires an authorized actor, reason, evidence, original decision, replacement decision, affected order, and audit event.

No UPDATE of the original attribution decision is permitted.

16. COMMISSION RULE CONTRACT

Initial commission rules are configuration, never hard-coded constants.

Rule selection precedence:

1. explicit product + affiliate-specific approved override;

2. Strategic Partner rule;

3. campaign-specific rule;

4. product-specific rule;

5. product-class rule;

6. default approved rule.

Within the same precedence class, the valid rule with greatest explicit priority wins.

Equal-priority overlapping rules at the same precedence level are a configuration error.

Result:

COMMISSION_RULE_UNRESOLVED

→ quarantine

→ no commission entitlement is created until resolved.

Rule effective time shall be evaluated using qualifying transaction timestamp.

Future lower rates cannot retroactively reduce an already earned commission.

    = gross merchandise line amount

      - allocated/order line discounts

    = net_merchandise_before_refund

      - refunded eligible merchandise amount

      - cancelled/reversed merchandise amount

    = remaining_eligible_merchandise

- shipping unless separately governed commissionable in future;

- non-eligible product lines;

- cancelled amounts;

- refunds;

- chargebacks;

Discounts

19. COMMISSION LIFECYCLE

Permitted normal transitions:

PENDING → APPROVED → PAYABLE → PAID

Exceptional transitions:

PENDING → DISPUTED

APPROVED → DISPUTED

PAYABLE → DISPUTED

PENDING → REJECTED

DISPUTED → APPROVED

DISPUTED → PAYABLE

DISPUTED → REJECTED

PENDING/APPROVED/PAYABLE/PAID → REVERSED

PAID is only applied after external payment execution is confirmed.

Invalid transitions shall return a deterministic error, create an audit event where material, and make no financial mutation.

- currency;

- resulting economic balance;

- event type;

21. HOLD PERIOD

Initial MVP hold:

30 days

Start event:

the authoritative qualifying transaction reaches the governed paid/completed state.

hold_until = maturity_start_at + 30 days

A scheduled process evaluates PENDING commissions.

To mature:

- current time >= hold_until;

- affiliate entitlement remains valid;

- no unresolved refund;

- no chargeback/payment reversal;

- no active dispute;

- no applicable compliance hold;

- commission has positive valid balance;

- source order remains qualifying.

Then:

PENDING → APPROVED

and, if payout conditions independent of the $50 aggregate threshold are satisfied:

APPROVED → PAYABLE

The $50 threshold governs batch inclusion, not whether an otherwise mature commission may be identified as payable.

22. REFUNDS, REVERSALS, CHARGEBACKS

Full refund before payment

Create COMMISSION_FULL_REVERSAL.

Original commission and ledger history remain.

Commission becomes REVERSED.

Partial refund

Recalculate qualifying revenue for affected lines.

required_reversal = original_valid_commission - recalculated_valid_commission

Append COMMISSION_PARTIAL_REVERSAL.

Never recalculate using current rates. Use the historical rate/rule applicable to the original sale.

Refund after payout

Append reversal event.

The paid historical event remains.

The reversed value becomes an affiliate-account debit adjustment against future payable balance unless another approved recovery method applies.

Chargeback/payment reversal

Confirmed lost revenue invalidates the affected commission amount.

Create reversal or rejection according to prior state.

Do not delete commission.

Duplicate refund

A refund event uses source-event idempotency.

Reprocessing returns the previously produced result and does not create a second reversal.

Affiliate processing must be feature-gated.

Minimum independent controls:

- referral route intake enable/disable;

- new attribution-context creation enable/disable;

- affiliate commission processing enable/disable;

- payout submission enable/disable;

- affiliate-facing portal enable/disable.

Disabling Affiliate functionality must not disable:

- WooCommerce checkout;

- normal Woo orders;

- bros.revenue_event.v1;

- Native CRM;

- Budly non-affiliate capabilities;

- CCSS;

- STS marketing attribution;

- non-affiliate sales.

Revenue events received while commission processing is intentionally disabled must remain preserved and explicitly marked for governed later processing or non-processing. They shall not vanish.

Schema rollback shall not destroy historical affiliate financial data.

Deployment rollback must prefer application rollback/feature disablement over destructive database reversal once financial records exist.

45. SECURITY REQUIREMENTS

- Server-side secrets only.

- No secret in referral URL.

- No secret in QR.

- No commission amount accepted from browser as authority.

- No affiliate class accepted from browser as authority.

- No rate accepted from browser as authority.

- Signed webhook/authenticity verification remains mandatory for upstream integrations.

- RLS plus backend authorization is required.

- Least privilege.

- Sensitive logging minimized.

- IP information, where justified, should be hashed/minimized.

- Tax documents excluded from general datastore.

- Customer PII excluded from affiliate-facing responses.

- Admin financial actions require authenticated actor identity.

- Human approvals require durable evidence.
